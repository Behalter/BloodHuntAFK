# Blood Hunt AFK bot: how the code works

Notes for whoever (human or agent) edits the code. `CLAUDE.md` has the project history, the user's decisions and the pending work; this file describes the code as it is.

Settings are named here, not given values: the values live in `bloodhunt/settings.py` (each with a comment; in the release, the `settings.py` next to the exe), and the user tunes them, by hand or in the window. Click spots and waits live in `profile.json`; the smelt rating is a setting (`SMELT_RATING`), the same for every profile. Numbers below are measurements and test results.

## What it does

It farms Marvel Rivals' **Blood Hunt** PvE mode solo, on Windows, overnight. The user's Thor build clears runs as long as **F (Awakening Rune)** is pressed on a timer, with **X (heal)** pressed during the rune's cooldown. One round:

1. **Match:** first F soon after the HUD shows, then F every `F_DURATION` + `F_COOLDOWN`, with X through each cooldown.
2. **MVP animation:** wait.
3. **Victory/Defeat screen:** click the SPACE box next to "HOLD TO SKIP" (a fixed spot).
4. **"One more round":** click it. It comes back **dimmed** just before character select, and the bot doesn't click it then.
5. **Character select:** nothing. The game picks Thor.

When loot storage is full, "One more round" doesn't start a round, and a message shows briefly. When the bot sees that message (a `routine_storage_full` template), or One more round is still there after `BACKUP_ROUTINE_AFTER` clicks (the backup), it runs the **storage-full routine** from the profile: Prepare → Forge → Filter → click the rating box and type the rating → Confirm → Select All → Smelt → Confirm (the Legendary warning) → Space → Overview → Play Now → Start. Then it carries on.

It reads the screen instead of replaying recorded inputs. Every `SCAN_EVERY` it takes a screenshot and looks for small images ("templates") the user cropped from their own screenshots. A template's **filename prefix** decides what happens when it's seen.

## Requirements and running

- Windows only. Python 3, with `pip install -r requirements.txt` (mss, opencv-python, numpy, pydirectinput, pinned) in a `.venv` in the project folder. Or the release: `BloodHuntAFK.exe` (the window) and `BloodHuntAFK-console.exe` (the commands), built by `build.ps1` (see The exe).
- `python BloodHuntAFK.py` with no command opens the window (`gui.py`, below). `python BloodHuntAFK.py <command> [--profile NAME]` runs a command; `help` prints the usage text. Simulated input has been confirmed to work at normal privilege on the user's machine.
- `--hold` (any command): wait for Enter at the end. The window's Setup tools add it, because they open the command in its own console window, which would otherwise close with the last message. Every command first reads `settings.py` through `settings_file.load()` (`commands.load_settings`): a mistake in it stops with its line number.

```
keytest            5 s countdown, presses F the way `run` does (`press_repeated`), prints the foreground window title/class
snap               F8 = save a screenshot to the profile's shots\ (and print every template's score), F10 = quit.
                   No profile for this screen shape: makes an empty one, named after the shape (16x10).
                   On a size the profile wasn't cropped at, says the shots are for `check` only.
                   Prints guide.checklist(): the screens to capture, and which templates are done
crop               guided (guide.guided_crop): each screenshot with a menu drawn on it; press the item's
                   number, box it (an example from another profile shows alongside); D = check an existing
                   template on this screenshot, N/Enter = next, Q = quit
crop NAME [SHOT]   pick one of the profile's screenshots (or give one), drag a box -> templates\NAME.png + NAME.json
check [SHOT]       score every template vs the live screen (5 s countdown) or a screenshot;
                   writes debug\check.png (green match, red no match, yellow search area, magenta click spot)
run                the farming loop. F8 = pause/resume, F10 = quit
routine check      draw each routine step's click (numbered magenta cross) on its screenshot -> debug\routine_<name>_NN.png
routine run        do the routine once now (5 s countdown; start on the Victory/Defeat screen), then exit
routine record     the user does the routine by hand; their clicks become its click spots (guide.record)
```

## Profiles (one per screen shape)

```
profiles/<name>/profile.json   {"screen": [1920, 1080], "click_at": {...}, "routines": {"storage_full": [steps]}}
profiles/<name>/templates/     NAME.png + NAME.json  {"x","y","w","h","screen_w","screen_h"}: where it was cropped
profiles/<name>/shots/         screenshots from snap
profiles/<name>/routines/<routine>/   the screenshots each routine step was measured on
```

- `screen` is the size the profile was cropped at (`Profile.base`). `click_at` and routine clicks are in that size's pixels.
- `click_at`: buttons clicked at a fixed spot instead of the centre of the match. `click_skip` needs it because matching finds both SPACE boxes (the NEXT one scores 0.895).
- `routines`: name → steps, in order. A step is `{"name", "click": [x, y] | "key": "space" | "type": "<text>", "wait": seconds after it, "shot": file in routines/<routine>/, "hint": what to click, in words}`. Validated on load (`profiles._step`). In `"type"`, `{SETTING}` is typed as that setting's value (`routines.typed`): the storage-full routine's rating step is `"{SMELT_RATING}"`, so the rating is one setting for every profile (the user, 2026-11-23; before, each profile's step held the number, which `routine record` copied and then each profile kept its own). `_step` checks the literal text and that the setting exists; the value is checked before each run (`routines.check_typing`: at `bot.run` start, `routine run`, `routine record`), since settings change between runs. A step with a plain number still works. `Profile.save()` writes the file back one step per line, in a fixed key order (`_step_line`); the guided crop (`click_at`) and `routine record` use it.
- **Names:** profiles are named after the screen shape: `16x9`, `16x10`, `4x3`, `5x4`, `3x2`, `32x9` (`SHAPES`, `shape_name()`), or `WxH` for any other shape (ultrawides vary: 2560x1080 and 3440x1440 aren't within 1% of each other). `--profile NAME` can still make a named one. History: `1080p` → `1920x1080` → `16x9` (2026-11-21/22; the user asked for one profile per shape).
- `shots/` and `routines/` aren't in git (they show the user's in-game UID; see `.gitignore`).
- The 1920x1080 step screenshots came from the user in chat. They're **1919x1079, missing the leftmost column**, so screen x = screenshot x + 1, and the stored clicks already include the +1. They also went through a different capture path: the real One more round template scores only 0.84 on them. Use them for click positions only, never for cropping templates.
- **Choosing** (`profiles.choose(name, size, create_new)`, not yet fitted): `--profile NAME` if given. Otherwise a profile whose `screen` is exactly this size (several: exit, "pick one with --profile"); else one of the same shape (`same_shape`: aspect ratios within 0.01), the one with the most templates, then the biggest. With none, `create_new` (snap, routine record) makes an empty one named after the shape; otherwise exit with "run snap". With a screenshot (`check SHOT`, `crop NAME SHOT`): the profile folder it's in, else the profile for its size.
- **Fitting** (`Profile.fit(size)`, `profiles.fitted()`): the profile for a screen of another size of the same shape. A shallow copy with `screen` = that size, `scale` = (sx, sy), `base` = the cropped size, and `click_at` / routine clicks multiplied by sx, sy and rounded. `templates()` then loads each template resized (`vision.load_templates(folder, size, base)`): each one is scaled from its own `screen_w/h`, else `base`, so the spot it's searched around moves too. Nothing is written; `save()` on a fitted copy raises. Different shape: exit, it needs its own profile. `fit()` to the same size returns the profile itself.
- **Who fits:** `run`, `snap`, live `check` and `routine run` fit to the main screen; `check SHOT` fits to the screenshot's size. `crop` (both kinds), `routine check` and `routine record` work on the profile itself, in its own pixels: crop only takes screenshots at the profile's size (`guide.not_cropped_here` explains, and suggests `snap --profile WxH` for an exact-size profile if a resized image scores too low); `routine check` draws on the step screenshots, which are at the profile's size; `routine record` converts each click to the profile's pixels (x · base/screen, using the screen size at that click) and resizes its screenshot to the profile's size.
- **The screen can change size under the bot.** A game in exclusive Fullscreen at another resolution than the desktop switches the display to it when it comes to the front, and Windows switches back when you alt-tab out. Found on the real game (2026-11-22): `run` read 1920x1080 in the terminal, the game then ran at 1280x720, and nothing matched. So the size is read when it matters, not once in the terminal: `Screen.refresh()` re-reads the game's picture (see Input and Windows plumbing), and reopens mss if the desktop's layout changed (mss keeps the layout it read at start). `bot.run` calls it before every screenshot and, **only while the game is in front**, re-fits when the screen isn't the size the profile is fitted to: `refit(size)` (from `commands.run`: `profiles.fitted(name, size)`, which re-picks, so an exact-size profile still wins), then reloads the templates and logs "the screen is now WxH - using profile ...". While the game isn't in front, nothing is sent anyway, so alt-tabbing back and forth doesn't re-fit each time. No profile for the new shape: logs why and stops. Live `check` and `routine run` read the size after their countdown; `snap` re-checks it at each F8; `routine record` at each click.
- **Resampling** (`vision.resample`): an affine warp that samples the template exactly onto the new screen's pixel grid, starting on an even pixel, after a slight blur when shrinking. A plain `cv2.resize` left the content up to a pixel out of step with the real screen and cost small templates a lot (the SPACE box at 1280x720: 0.69 vs 0.99). A template under 12 px at the new size is skipped with a log line. Tested on the user's 1080p screenshots resized to 720p/768p/900p/1440p/4K: everything that should match scored 0.87–1.00, wrong matches at most 0.58. A resized screenshot isn't the game rendering at that size, so it's a best guess until the user checks it on the real game; `run` logs that the profile is resized. Resizing 5 templates takes milliseconds, which is why there's no cache on disk (an earlier version wrote a scaled copy per size; replaced because a copy goes stale when the source is re-cropped).
- A different shape (16:10, ultrawide) isn't scaled, because the game's UI layout changes: those need `snap` → `crop` → `routine record`, and the result then fits every size of that shape.
- `16x9` (cropped at 1920x1080) holds `click_one_more_round`, `click_skip`, `ingame_lshift`, `ingame_portrait`, `routine_storage_full` (cropped by the user from the real message), and the `storage_full` routine.

### Template naming = behaviour

The prefix match is case-insensitive. Other names are ignored, with a log line.

| Prefix | Meaning |
|---|---|
| `click…` | Click it when it's visible and not dimmed (at its `click_at` spot, else its centre) |
| `ingame…` | While any is visible we're in a match: the F/X timer runs. With **no** `ingame` templates, every screen counts as a match |
| `stop…` | Save a screenshot and stop the bot |
| `routine_<routine>…` | Run that routine from `profile.json` (e.g. `routine_storage_full.png` → `storage_full`; the longest matching routine name wins). One that matches no routine is ignored, with a log line |

## The loop (`bot.run`)

Each iteration, in order:

1. **Hotkeys and limits.** Poll F8/F10. Stop after `MAX_HOURS`.
2. **Focus.** If the game isn't the front window, the bot skips all input and **never steals focus**. Exception: after `IDLE_BEFORE_REFOCUS` with no mouse/keyboard input, it brings the game back with `ensure_focus()`, at most every `REFOCUS_EVERY`. **When the game is back in front** (you clicked back in, or `ensure_focus` succeeded), it sleeps `FOCUS_SETTLE` and starts the iteration over, so the first input comes after the wait, based on a fresh screenshot. Reason: games often swallow input right after regaining focus; that's how a skip click was lost on the real game. `act()` refuses input while `away_since` is set, so nothing slips through between noticing the return and the wait.
3. **Capture.** `screen.refresh()`, and while the game is in front, re-fit the profile if the screen size changed (see Profiles). `mss` grabs the game's picture (`Screen.mon`), converted BGRA → BGR, shrunk by `MATCH_SCALE`. On the first frame with the game in front (and after a re-fit), `warn_size` logs any image sized for another screen than the frame; with fitting, that's only an image cropped at another size than the rest of its profile. If a screenshot was requested for "the next frame" (`save_next`, see the streak below), it's saved now.
4. **After a routine:** if nothing has been recognised `ROUTINE_RECOVER` after the routine finished, save `debug/routine_failed_*.png` and stop.
5. **Stop signs.** Any `stop` match: save `debug/stop_*.png`, stop.
6. **Routine triggers** (before buttons). A `routine_*` match: save `debug/routine_<name>_*.png`, run the routine (below), then `presses = None`, clear the button state, and start the `ROUTINE_RECOVER` clock. If a trigger is seen again **before any match has started** since the last routine (smelting freed nothing), stop instead of looping.
   - **Backup** (built 2026-11-22; agreed by the user 2026-11-21): One more round (`bot.BACKUP_BUTTON`), once its click streak has reached `BACKUP_ROUTINE_AFTER` and it's armed and still there (not dimmed), runs the `storage_full` routine instead of being clicked again. Same rules as a trigger (the "again before a match" stop, the recovery clock). Reason: the message can be missed, and at 720p its template doesn't match at all (see Image matching), but One more round that never starts a round always means full storage. With only the backup (no trigger match), smelting that frees nothing ends with Start doing nothing on the Play screen, so the `ROUTINE_RECOVER` stop catches it. Cost: storage-full is caught after 3 clicks (about 20 s) instead of at the message. Worst case of a false trigger (One more round ignoring clicks for another reason): gear at or below the rating smelted early, accepted by the user.
7. **Buttons.** The best-scoring armed, not-dimmed `click` template is clicked, then the mouse goes back to the screen centre (where the game leaves it). After a click: `presses = None`, wait `AFTER_CLICK_WAIT`, `continue`. Buttons in `AFTER_CLICK_WAIT_FOR` wait less: "One more round" is in it, because the storage-full message only shows briefly. While the clicked button is still visible, the bot keeps scanning every `SCAN_EVERY`, so it looks for the message several times before the retry.
   - **Retry:** a clicked button is disarmed for `REPEAT_CLICK_AFTER`. If it's still on screen after that, it's clicked again, on the first scan after it re-arms. While disarmed and still visible, the bot just waits.
   - **Streak:** clicking the same button again without it ever leaving the screen counts as a retry (logged as "try N"). On the `NO_EFFECT_AFTER`th click it saves one `debug/noeffect_<button>_*.png` of the **next** frame, i.e. what the screen shows the after-click wait later (short for One more round, so with full storage it shows the message). Then it keeps retrying. The streak resets on any scan where no button is visible.
   - **Dimmed:** `TM_CCOEFF_NORMED` ignores brightness, so a dimmed button still scores about 1.0. `find()` also returns its contrast (std dev of the matched area / the template's). Under `CLICK_MIN_CONTRAST`, it's never clicked. Clicking it would be harmless (the user confirmed), but it's skipped anyway.
8. **In a match?** Any `ingame` template matches. Also clears "a routine ran and no match has started since".
9. **F and X** (`Presses`): only when in a match **and** the game is in front (and settled), the same rules for both keys.
   - First F `FIRST_PRESS_DELAY` after the HUD is first seen. It's timed from that sighting, and the bot wakes up exactly when F is due, so it doesn't need to line up with `SCAN_EVERY`. 0 = press on the same scan that first sees the HUD. After each F at time *t*: X every `HEAL_EVERY` from *t* + `F_DURATION` + `HEAL_DELAY_POST_F`, as long as it's before the next F (`bot.heal_offsets()`, logged at start; the user found two heals per cooldown weren't enough), and the next F at *t* + `F_DURATION` + `F_COOLDOWN`. Each is timed from the **actual** F press, so a late F moves everything after it.
   - Each F is `inputs.press_repeated`: `ABILITY_PRESSES` presses, starting evenly spread over `ABILITY_SPAN`, timed by the clock. A single F sometimes didn't fire; once it does, the animation stops the later presses from cancelling it (the user tested this). X is one press.
   - **No backlog:** a press that couldn't be made stays due and is made late, but only while it's the latest one due. When a later one is due too, only the latest is pressed and the earlier ones are dropped. There's at most one press per scan, so it never bursts. Consequence: an X made late shortly before the next X is due is followed by that X a moment later. Both were on the schedule.
   - HUD hidden (cutscene, death): nothing is pressed. If it's gone longer than `MATCH_LOST_GRACE`, the match counts as over (`presses = None`), and the next HUD starts over with the `FIRST_PRESS_DELAY`.
10. **Stuck watchdog.** Nothing recognised (button, HUD or stop sign) for `STUCK_AFTER` → `debug/stuck_*.png`, at most `STUCK_SHOTS_MAX` in a row until something is recognised again.
11. **Sleep** `min(SCAN_EVERY, time until the next press that isn't due yet)`. Overdue presses are retried at the normal scan rate. The old code slept 0.05 s and re-scanned constantly while a press was overdue. `Hotkeys.sleep()` polls hotkeys every 50 ms and doesn't return while paused (on purpose).

On exit it logs the runtime and counts (matches, clicks per button, F presses, X presses, routines).

`run(profile, refit, keys, status, start_delay)`. From the window: `keys` is the window's `Hotkeys` (its Pause/Stop buttons call `toggle_pause()` / set `quit`, the same switches F8/F10 flip), `status` a `Status` it reads, `start_delay` 0 (no countdown: step 2 already waits for the game to be in front). `Status` gets plain attribute writes only, because the window's thread reads it: `state` (in a match, clicked X, waiting for the game, running a routine, ...), `next_f` (when the next F is due, `Presses.next_f()`), `profile`, `started`, and `stats` (the Counter the exit line is made from; the window copies it before reading). `RUN_ROUTINES` off: no triggers (`sort_templates`) and no backup, logged at start. A profile without the `storage_full` routine is logged at start too (a new 16:10 profile before `routine record`).

## Routines (`routines.run`)

- Steps run strictly in order. Before **each** step, `wait_for_game()` waits until the game is the front window. It never steals focus, except after `IDLE_BEFORE_REFOCUS` of user idleness, the same as the main loop. If it had to wait, it sleeps `FOCUS_SETTLE` first. A step is never skipped, because the steps are a sequence.
- Click: `inputs.click(x, y)` with no mouse parking (nothing is matched during a routine, so hover doesn't matter). Key: `inputs.press(key)`. Type: `inputs.type_text(routines.typed(text), TYPE_GAP)` (settings filled in, e.g. `{SMELT_RATING}`; `bot.run` logs what it will type at start), one key press per character (~0.18 s each; `inputs.key_for` maps characters to keys, and `_step` rejects text with capitals or Shift symbols). Then sleep the step's `wait`. Waits are fixed: there are no per-step image checks yet (deferred by the user).
- F8 pauses mid-routine; F10 aborts it (and the bot).
- `storage_full` (steps, spots and waits in `profiles/16x9/profile.json`; its "Type rating" step types `{SMELT_RATING}`; the sequence and its reasons are in `CLAUDE.md`): the rating box is clicked first because clicking it selects the old value, so typing replaces it. When the Legendary popup doesn't show, its CONFIRM spot is empty background on both the Forge and Acquired screens, so that click does nothing. LEGENDARY's checkbox (800,378 at 1920x1080) must never be clicked. Run on the real game by the user (2026-11-21): works.
- `routine check` draws every step for eyeballing. `routine run` runs it once by hand.
- **`routine record`** (`guide.record`): the steps, waits, keys and typed text come from a profile that has the routine (this one if it has it, else a cropped one, `profiles.with_routine`); only the click spots are recorded. It prints every step (using each step's `hint`) and the rules: start on Victory/Defeat with PREPARE showing (START at the end could otherwise start another mode), have a Legendary item at or under the smelt rating (so the smelt popup appears; its CONFIRM is a click), make only those clicks. Then it polls the primary mouse button (`winapi.mouse_down`, swapped buttons respected) every 5 ms. At each click it re-reads the screen size (`screen.refresh()`). A click counts only if the game has been in front for 0.5 s (so the click that focuses it doesn't), it's on the main screen, and the screen is the profile's shape. Clicks and screenshots are stored in the profile's pixels. Each one beeps and grabs the screen, which is saved as that step's `shot` (first click per shot name), so `routine check` works on the user's own screen. F9 undoes the last click; F10 cancels without saving. After the last click: save to profile.json, draw the check images, and tell the user a round should now be starting, or else to record again. Key presses are never recorded; there's no screenshot for the SPACE step (nothing is clicked on that screen).

## Image matching

- `cv2.matchTemplate(..., TM_CCOEFF_NORMED)` on colour images, frame and template both shrunk by `MATCH_SCALE`. NaN/inf (flat areas) → 0.
- **Location lock:** a template with a `.json` is only searched for within `SEARCH_MARGIN` of where it was cropped, so the same picture elsewhere (Thor's portrait on character select) can't fool it.
- `crop` snaps boxes to even pixels (the `MATCH_SCALE` grid). An odd offset cost about 0.12 of score at half scale.
- `find()` returns `(score, centre in full-size screen pixels, contrast)`. `best()` returns the highest-scoring template at or above its threshold (`vision.threshold(t)`: `MATCH_THRESHOLD`, or `MATCH_THRESHOLD_SCALED` for a template resized to another screen size, `Template.resized`), optionally skipping dimmed ones. `report()` (snap, check) marks resized ones with the score they need.
- Matching is single-scale: a template only matches at the size it's loaded at. On another size of the profile's shape, templates are resized once when loaded (see Fitting); a different shape needs its own profile.
- Crop from `snap` screenshots (same capture pipeline as the live matcher), not the Snipping Tool.
- Real scores on the user's screenshots: matches 1.00, non-matches 0.06–0.42.
- **Resized images score lower on the real game than on resized screenshots** (2026-11-22). On a real 1280x720 Defeat screen (a Snipping Tool capture of the game window's 1280x720 area), `click_one_more_round` resized from 1080p scored **0.79**, in the right spot; the other images 0.20–0.44. The layout scales exactly (the button's size and place are right; two thirds is the best scale), but the game draws text at whole font sizes, so at 720p "ONE MORE ROUND" is slightly wider and lower than a shrunk 1080p copy, and text-heavy images lose the most. Tried and rejected: blurring the frame and template before matching (One more round 0.90 at sigma 0.75, but the small images fall apart, the LSHIFT label is about 16x7 at matching size, and wrong matches rise to 0.62). Chosen by the user: a lower threshold for resized images only (`MATCH_THRESHOLD_SCALED`); 1080p keeps `MATCH_THRESHOLD`. Margins seen: right 0.79 (real) / 0.87+ (resized screenshots), wrong at most 0.58. The SPACE box scored 0.92 at 720p in a real run; in a match at 720p (an mss grab from the user's second monitor) `ingame_portrait` 0.94, `ingame_lshift` 0.47.
- **The storage-full message at 720p scores 0.55** (real snip, 2026-11-22). Two reasons: the game spaces text about 4% wider at 720p (vertically everything is exactly two thirds: band top, text line and band bottom all line up), and the wider text wraps differently (at 1080p "some" ends line 1; at 720p it starts line 2). Tested: the whole message at the best size 0.68; first-line-only crops of the opening words (the user's idea, wrap-proof) 0.55–0.57 resized, 0.66–0.78 if also stretched 2–4% wider; pieces including the band's edges up to 0.79, but wrong matches rise to 0.50. None was reliable enough, so the backup trigger covers sizes where the message doesn't match.
- Images are read and written with `np.fromfile`/`imdecode` and `imencode`/`tofile`, because plain `cv2.imread` breaks on non-ASCII Windows paths.

## Input and Windows plumbing

- `pydirectinput` sends `SendInput` with scan codes. Key: down, 80 ms, up. Click: move, 150 ms (hover), down, 70 ms, up, then 100 ms and move to the screen centre. `PAUSE = 0.05`.
- **The game can be on any monitor** (2026-11-22; the user moved it to their second monitor to keep using the main one). `Screen` captures the **game's picture**: the inside of the game window (`winapi.game_area`: `GetClientRect` + `ClientToScreen` on the window found by `GAME_TITLE`/`GAME_CLASS`, so no title bar or borders), wherever it is. Every position (templates, `click_at`, routine clicks, `find()` results) is in that picture's pixels; `Screen.to_screen()` adds where it is on the desktop before a click, and `from_screen()` takes it off (`routine record`). `refresh()` re-reads it before each screenshot, so moving the window or changing its resolution is followed. While the game window isn't found (not running, minimised) it falls back to the main monitor, the one whose top-left is (0, 0) (mss doesn't reliably list it first; `monitors[1]` was the laptop screen on the user's machine).
- **Clicks on any monitor:** pydirectinput's `moveTo` maps 0–65535 onto the main monitor only, so it can't reach another one. `inputs.move_to` sends the same `SendInput` absolute move with `MOUSEEVENTF_VIRTUALDESK` added, normalised over the whole desktop (`winapi.virtual_screen`), with pydirectinput's rounding (+1), failsafe check and pause. The button down/up still go through pydirectinput. Checked in the simulation: every pixel lands exactly on 4 desktop layouts (incl. negative coordinates and the user's 3200x1080: main 1920x1080 plus a 1280-wide monitor to its right). Not yet run on the real game.
- Coordinates are in physical pixels on every monitor because the process is per-monitor DPI aware (below).
- Failsafe stays on: mouse into the top-left corner raises `FailSafeException`, which `main()` logs as a clean stop.
- DPI awareness (`SetProcessDpiAwareness(2)`, falling back to `SetProcessDPIAware`) is set in `bloodhunt/__init__.py`, before `mss` and `pydirectinput` are imported, so captures and clicks are in physical pixels on scaled displays.
- `is_game()`: the title contains `GAME_TITLE` ("Marvel Rivals"; the real title is "Marvel Rivals  ") **and** the class is `GAME_CLASS` ("UnrealWindow"). Both have been confirmed on the real game.
- `ensure_focus()` restores the game if minimised, taps Alt around `SetForegroundWindow` (Windows only lets a background process take focus right after a key event), waits 0.5 s and re-checks.
- Hotkeys use `GetAsyncKeyState` polling, so they work while the game has focus.

## The settings file (`settings_file.py`)

- **One file holds every value** (the user, 2026-11-23: "settings.py so it's just a single file"): `bloodhunt/settings.py` from source, `settings.py` next to the exe in the release (`PATH`). The exe can't import a file from its folder (PyInstaller bakes the bundled module in), so the file is **read, not run**: `ast.parse`, and every line must be `NAME = value` with a plain value (`ast.literal_eval`: numbers, strings, True/False/None, dicts). `load()` puts the values into the `settings` module (`setattr`), which every module reads as `cfg.NAME` at the moment it needs it; a setting missing from the file gets its built-in value (`DEFAULTS`, the module's values before any load). `check_kinds` rejects a value of the wrong kind (text where a number was) with its line, so a hand-edit slip is reported at start instead of crashing mid-run; `NONE_OK` lists settings that may be None.
- **Help text:** each setting's comment (on its line, the indented comment lines under it, and inside its `{...}`). A comment starting with `...` continues the setting above (`Setting.group`), so the window shows them together. `# ── Name ──` starts a section; a parenthesis in it, and column-0 comment lines right under it, describe the section. That's why some comments were reworded on 2026-11-23 to read on their own (`ABILITY_SPAN`, the hotkeys).
- **`save(changes)`** replaces only the text of each changed value (from the ast node's position; columns converted from UTF-8 bytes), right to left within a line, keeping the comment's column when there's room (also after a `{...}` entry's comma). `{(NAME, key): value}` changes one entry of a dict; a whole dict can't be replaced. Unchanged values are skipped (`0.80` stays `0.80`). Key codes keep their hex style. Line endings are kept. The result is parsed and checked before it replaces the file (written to `settings.py.tmp`, then `os.replace`).
- `ensure_file()`: in the exe, a missing `settings.py` is replaced by the built-in copy (`BUNDLE/defaults/settings.py`, added by the spec).
- A UTF-8 byte-order mark (Notepad's "UTF-8 with BOM") is accepted when reading (`utf-8-sig`; Python's parser rejects it otherwise) and kept on save. A save where every value is already what it's set to doesn't touch the file.

## The window (`gui.py`)

- tkinter (no extra dependency). Opened by `BloodHuntAFK.py` with no command (`commands.main` → `gui.main`), and by both exes with no command.
- **Threads:** Start, Key test and Check screen run the existing commands (`commands.run` with `keys`/`status`/`start_delay=0`, `commands.keytest`, live `commands.check`) in a worker thread. Tk is touched only from the main thread: the worker reaches it through a queue (`events`: printed text, errors, done) and the `Status` object, which `poll()` reads every `POLL_MS`. `sys.stdout`/`stderr` are replaced by `_Output`, which feeds the log box (and still writes to a console if there is one), so every `log()` line and `check`'s scores show up. A `SystemExit` from the worker (no profile, no templates) becomes an error box; any other exception is logged with its traceback.
- **Setup tools** (snap, crop, `check SHOT` with a file picker, routine record/check) open the command in its own console window (`CREATE_NEW_CONSOLE`; `BloodHuntAFK-console.exe` in the exe, else `python.exe BloodHuntAFK.py`), with `--hold` and the window's `--profile`. They're keyboard- and OpenCV-window-driven, so they weren't rebuilt in Tk. While one is open, the bot's buttons wait (both would poll F8/F10 and the screen).
- **Fields:** the Settings tab is `MAIN` (the user's split, 2026-11-23): ability key/duration/cooldown/first press/presses; heal key/first heal/interval; when storage is full (`RUN_ROUTINES`, `SMELT_RATING`, `BACKUP_ROUTINE_AFTER`); `MAX_HOURS`; the three hotkeys. The Advanced tab has every other setting, under the file's sections, so a setting added to the file appears there by itself (labels from the name). `HIDDEN`: `MATCH_SCALE` (the crops are aligned to it). Dict settings get one field per entry. Field kind comes from the value (bool, number, text) and the name (`GAME_KEYS` = pydirectinput key names; other `*_KEY` ints = virtual-key codes). Numbers accept a comma as decimal point; `RULES` adds whole-number / range checks. Cross-checks: ability key ≠ heal key; hotkeys all different, and never a key the bot presses itself (the ability/heal keys, Space, digits: `GetAsyncKeyState` sees the bot's own `SendInput`).
- **Key fields:** click, then press the key. On Windows, Tk's `event.keycode` is the virtual-key code, mapped to pydirectinput's names by `winapi.VK_NAMES`. Esc keeps the old key; a key pydirectinput can't send is refused.
- **Saving:** Save (and Start, Key test, Check screen and Setup tools, which save first) writes only changed fields (`settings_file.save`), then re-reads the file. With no `storage_full` routine in the profile in use (read from its `profile.json` as it is now), the storage fields are greyed out and a note says full storage isn't handled; a routine that types a rating of its own instead of `{SMELT_RATING}` (an older profile) gets a note that the setting isn't used there. Otherwise there's no note (the user, 2026-11-23: how things are stored isn't something a player needs). Fields lock while anything runs. Once a second while idle: if `settings.py` changed on disk, it's re-read (or, with unsaved edits, a warning; Save then keeps both, since only changed values are written); the profile is re-picked when the game window's size changes (same rule as `run`: game window, else the main monitor).
- **Status:** profile, game window (found / size / in front), state and next F, counts. Not running as admin: a red line. The window title must not contain `GAME_TITLE`, or the window would count as the game.
- `report_callback_exception` logs Tk callback errors. `BLOODHUNT_GUI_SELFTEST=<file>`: build the window hidden, write what it built to the file, close (for checking a built exe, which has no console).
- DPI: the process is per-monitor DPI aware (`__init__.py`), so Tk fonts come out at the right size; paddings are scaled by `px` (pixels per 1/96 inch).
- **Layout rule: no widget's size may depend on its text** (fixed 2026-11-23, reported by the user: the columns jumped while pointing at fields, and resizing lagged). Grid sizes a column by what its widgets ask for, so the help label asking for the width of its current text moved the split on every hover. Wrapping it at its box's width (a `<Configure>` binding on the box) also fed back on every resize step: box width → wrap → label width → box width, several layout passes per step. Now: the two columns share the width in a fixed 5:4 (`uniform`); text widgets are made with `width=1` (they ask for no width and fill what they get); wrapped labels wrap at their own width (`App._wrap`, only when it changed by more than 2 px); the help label has a fixed height of 7 lines; the log box and the tab canvases ask for 1x1. `layout_test` checks that pointing at fields, long help/status/save texts and resizing move nothing, and that a resize step lays the help label out once.
- **Resizing still costs about 1 ms per visible widget per step** (measured 2026-11-23): Tk on Windows redraws every visible widget on each resize step, also widgets whose frame didn't change size, whatever the widget type or theme (75 ttk or tk labels ~80–100 ms, an empty window ~5 ms). The window has ~75 visible widgets, so ~100–125 ms per step on screen. Off-screen windows aren't painted, so timing must be done on screen (transparent and lowered). Not fixable from Python short of fewer widgets or another toolkit.

## The exe (`BloodHuntAFK.spec`, `build.ps1`)

- PyInstaller, **one folder** (one-file unpacks itself to a temp folder on every start, which is slower and more often flagged by antivirus), zipped. Two exes from the same analysis share `_internal\`: `BloodHuntAFK.exe` (`console=False`) and `BloodHuntAFK-console.exe`. Both have `uac_admin` (they ask for admin on start) unless built with `-NoAdmin` (`BLOODHUNT_NO_ADMIN=1`, for test builds). OpenCV's ffmpeg video plugin is left out (~40 MB, never used). PyInstaller is pinned in `requirements-build.txt`.
- `build.ps1` copies next to the exes: `settings.py`, `README.md`, and for each profile only `profile.json` and `templates\*.png|*.json`. Never `shots/`, `routines/`, `debug/`, `bot.log`. The zip-step retries, because antivirus locks freshly written files for a moment.
- Releases: `.github/workflows/release.yml` runs `build.ps1` on `windows-latest` for a pushed `v*` tag and creates a **draft** release with the zip (`gh release create --draft`); the user tests it and publishes. Not yet run on GitHub.
- Unsigned: SmartScreen warns, and some antivirus may flag it. Nothing is done to avoid that (see `CLAUDE.md`, Context and boundaries).
- First build (2026-11-23): 147 MB unpacked (mostly `cv2.pyd`), 57 MB zipped. `BloodHuntAFK-console.exe check` on the user's 1080p screenshots gave exactly the same scores as from source; the window self-test passed in both exes; a deleted `settings.py` is put back, and a wrong value is reported with its line.

## Things to be careful with when editing

- Keep the DPI setup in `bloodhunt/__init__.py`, ahead of any `mss`/`pydirectinput` import.
- `find()` expects an already **shrunk** frame. Don't shrink twice, and scale coordinates back up.
- Clicks go through `screen.to_screen(pos)` (monitor offset) and through `act()` (focus and settle).
- `presses = None` means "no match in progress". Reset it after clicking a button and after `MATCH_LOST_GRACE`.
- Settings are read as `cfg.NAME` at call time, so changing `settings.py` (or patching it in a test) takes effect everywhere. Don't copy a setting into a module-level constant or a default argument: `settings_file.load()` changes the module's values after import (in the exe, always).
- `settings.py` must stay plain `NAME = value` lines (no expressions, imports or code): the exe reads it with `ast.literal_eval`. Write each setting's comment so it reads on its own, since it's the window's help text (start with `...` to continue the one above).
- In `gui.py`, touch Tk only from the main thread; the worker talks through `events` and `Status`.
